# GraspNet + nvblox + CuRobo minimum validation demo

## 1. Goal

This package is a plan-only, repeatable A/B experiment for the right RealMan RM65. It answers one
question: with an identical start state and grasp goal, does the nvblox ESDF actually change the
trajectory generated by CuRobo, preserve configured clearance, and reject a fully blocked path?

Starting ROS nodes is not considered proof. The supplied summary reports `VERIFIED` only after all
manual and physical tests satisfy the strict comparisons below.

The package never publishes a RealMan motion command. `execute_trajectory:=true` is rejected at
startup.

## 2. Architecture

```text
Mock fixed T_right_base_goal ---------------------------+
                                                        |
GraspNet PoseStamped (camera frame, image timestamp)    |
        |                                               v
        +-- exact timestamp TF -- T_grasp_tool --> /grasp_pose_base
                                                        |
RGB-D aligned depth --> nvblox --> ESDF service --------+--> CuRobo MotionGen
                                                        |    IK + collision + TrajOpt
/right/joint_states ------------------------------------+            |
                                                                     +--> /planned_trajectory
                                                                     +--> RViz markers
                                                                     +--> JSON + CSV metrics
```

GraspNet and nvblox are parallel consumers of the same RGB-D system. nvblox runs continuously;
GraspNet or the mock producer supplies a goal independently. No sequential stop/start pipeline is
implemented.

## 5. Coordinate frames

The generic task uses `base_link`, but this machine's controller-aligned right-arm frame is
`right_base`. All three required frames are therefore configured as:

```text
CuRobo planning frame = right_base
nvblox global frame   = right_base
final grasp frame     = right_base
```

The reused CuRobo URDF root is `driver_base`; validation launch publishes an identity
`right_base -> driver_base` only for RobotModel display. Any grasp or nvblox mesh frame mismatch
stops planning with `[FATAL FRAME MISMATCH]`.

## 6. GraspNet output contract

Mock mode publishes a fixed, measured-near-current goal from `config/test.yaml`. It does not change
between collision-on and collision-off experiments.

Real mode expects `/grasp_pose_camera` with:

```text
type: geometry_msgs/msg/PoseStamped
header.frame_id: right_camera_color_optical_frame
header.stamp: original RGB/depth acquisition timestamp (nonzero)
pose: T_camera_grasp
```

The node computes:

```text
T_right_base_tool_goal = T_right_base_camera(t_image) * T_camera_grasp * T_grasp_tool
```

`T_grasp_tool` is explicit in `config/test.yaml`. Exact timestamp TF lookup failure logs
`[ALIGNMENT ERROR]` and `TF_ERROR`; latest TF is never used as fallback.

The legacy `grounded_sam2_ros2/graspnet_bridge.py` JSON output does not retain image time and is not
used here. `timestamped_graspnet_node.py` supplies the corrected boundary: it caches aligned depth
and CameraInfo by the complete `(sec, nanosec)` key, accepts only a Grounded SAM2 mask with that
exact key, runs the existing GraspNet checkpoint, and publishes the camera-frame `PoseStamped` with
the unchanged acquisition stamp. A missing match is rejected as `TF_ERROR`; latest data is never
substituted.

## 7. RGB/depth alignment and nvblox

The right camera launch enables RealSense alignment and synchronization. nvblox consumes:

```text
/right_camera/right_camera/color/image_raw
/right_camera/right_camera/color/camera_info
/right_camera/right_camera/aligned_depth_to_color/image_raw
/right_camera/right_camera/aligned_depth_to_color/camera_info
```

Raw unaligned depth is not used. nvblox performs static TSDF integration and 3D ESDF updates in
`right_base`. The bridge verifies the mesh frame, exact `x/y/z` multi-array labels and strides,
voxel size, observed voxel count, and finite/unobserved values before updating CuRobo.

## 8. cuRobo inputs and collision world

The node reuses `curobo_realman_test/config/rm65.yml` and `rm65.urdf`. MotionGen receives current
six-joint state, the fixed goal, and one of these world modes:

```text
none             all world obstacles disabled
manual_cuboid    configured Cuboid enabled in CuRobo's primitive checker
nvblox           ESDF converted to a CuRobo VoxelGrid
```

nvblox uses positive distance in free space. CuRobo's voxel representation uses positive values
inside collision space, so the injected feature is:

```text
feature = nvblox_collision_margin_m - nvblox_esdf
```

No avoidance waypoint or direction is generated by this package. MotionGen's collision checking
and trajectory optimization choose the path.

After a successful plan, every interpolated joint point is passed through CuRobo FK. Every robot
collision sphere is queried again with `world_coll_checker.get_sphere_distance(...,
compute_esdf=True)`. The reported clearance is for the complete robot and complete trajectory, not
only the end-effector or terminal pose.

The reused RM65 collision spheres are preliminary and self-collision checking remains disabled to
match the existing validated planner. This is a known model limitation, not hidden evidence.

## 9. RViz robot and planned-motion replay

The validation launch publishes two copies of the same `rm65.urdf`:

```text
/robot_description          -> live RobotModel, driven by /right/joint_states
/planned/robot_description   -> planned RobotModel, driven by /planning_debug/joint_states
```

The planned copy uses the `planned_` TF prefix and is connected by an identity
`right_base -> planned_driver_base` transform. The URDF itself still contains the CuRobo
`driver_base -> base_link` rotation of `rpy="0 -pi/2 0"`; therefore the live and planned copies
use exactly the same controller-aligned base convention. The planner reads `/right/joint_states`
when `/planning_test/run` is called, and the first replayed planned joint state is that measured
start state. No replay topic is connected to `rm_driver`.

Start RViz together with the validation launch:

```bash

  use_mock_grasp:=true \

  enable_nvblox_collision:=true \

  launch_rviz:=true
```

After the camera/nvblox map is ready, call the planning service. RViz will show the live blue
model, the semi-transparent planned model moving from the measured start state, the green EE path,
the grasp arrow, and the nvblox mesh:

```bash

```

For the real camera path, start the equivalent processes only once and use real GraspNet input:


## 15. Results and summary

Each call writes `/home/lh/robot/validation_results/test_NNN.json` and, on success, a matching CSV:

```text

```

JSON includes planning status/time, trajectory points, joint and Cartesian path lengths, minimum
clearance, start state, goal, nvblox statistics, collision mode, unknown-space policy, a planning
parameter snapshot, and a sampled trajectory signature.

Generate the strict summary:

```bash

  /home/lh/robot/validation_results --write-json
```

It reports `VERIFIED` only if all six result records (including the two Test 0 halves) exist and:

- Test 0 paths differ with identical start/goal.
- Test 1 succeeds with a valid nvblox world.
- Test 2 succeeds, differs from Test 1, and meets clearance.
- Test 3 rejects planning with collision enabled and a valid world.
- Test 4 succeeds with collision disabled and differs from Test 2.
- Compared runs retain the same start, goal, planning parameters, and unknown-space policy.

Every failed check prints a concrete reason. Missing physical runs never default to success.

## 18. Failure categories

The result uses these categories where applicable:

```text
GRASPNET_ERROR  TF_ERROR  NVBLOX_ERROR  ESDF_ERROR  ROBOT_MODEL_ERROR
IK_ERROR        COLLISION_ERROR         TRAJECTORY_OPT_ERROR
GOAL_IN_COLLISION  START_IN_COLLISION   NO_VALID_PATH
```

Common diagnosis:

- `TF_ERROR`: goal, mesh, or configured planning frames differ; or exact image-time TF is absent.
- `NVBLOX_ERROR`: service/mesh unavailable, insufficient observed voxels, or no frame evidence.
- `ESDF_ERROR`: wrong layout, data length, voxel size, or timeout.
- `START_IN_COLLISION`: robot collision spheres overlap observed/unknown space; inspect RViz and
  collision-sphere calibration before changing policy.
- Test 0 unchanged/failed: fix RM65 collision model or MotionGen configuration before nvblox.
- Test 2 unchanged: ESDF may not be injected, obstacle may miss the direct robot path, or the path
  signature comparison may have different inputs.
- Test 3 succeeds through the blocker: fail the experiment; do not claim verification.

## 20. Not implemented

- Automatic real-robot trajectory execution.
- Target-object removal or allowed gripper-target contact.
- Validated RM65 self-collision spheres.
- Automated physical placement/restoration of the Test 2/3/4 obstacle scenes.

The existing timestamp-less GraspNet JSON bridge is intentionally untouched; this package provides
the independent exact-time adapter used by Stage 4.

These omissions keep the validation focused and prevent unsafe or unverifiable behavior.
