# supermarket_pick_sequence 代码详细介绍

## 1. 项目概述

`supermarket_pick_sequence` 是一个基于 ROS 2 的双臂移动抓取任务协调包。它自身不重新实现 YOLO、Qwen、GraspNet、CuRobo、RM65 驱动或底盘驱动，而是通过 ROS 2 Topic、Service、Action 和反馈话题，把已有节点编排成一条可执行、可监控、可取消、可恢复的超市比赛流程。

系统覆盖以下硬件和算法：

- Woosh/AGV 移动底盘与导航标记点；
- RM65 左右机械臂及升降机构；
- 左右腕部 RealSense RGB-D 相机；
- YOLO 商品检测；
- Qwen2.5-VL 语义识别兜底；
- GraspNet 抓取候选生成；
- CuRobo IK、碰撞检查和轨迹规划；
- OmniPicker 左右夹爪；
- Qt 比赛控制台。

核心设计原则是：

> 只有一个模块决定流程，设备节点只执行动作并上报结果；只有经过当前状态校验的事件，才能推进任务。

主要代码入口：

| 文件 | 职责 |
|---|---|
| `supermarket_pick_sequence/competition_fsm_node.py` | ROS 2 节点、回调、命令分发、反馈转换、超时与安全控制 |
| `supermarket_pick_sequence/competition_fsm/state_machine.py` | 纯 Python Competition FSM、任务拆分、状态推进与重试 |
| `supermarket_pick_sequence/competition_fsm/config.py` | 读取任务配置并解析箱型/商品参数 |
| `supermarket_pick_sequence/competition_fsm/resource_manager.py` | 管理底盘、升降机、双臂、夹爪、相机和 GPU 资源 |
| `supermarket_pick_sequence/competition_fsm/adapters/*.py` | 导航、感知、规划和硬件事件的接口契约 |
| `config/competition_tasks.json` | 箱型、商品、YOLO 标签、Qwen 提示词、机械臂、点位、高度和角度 |
| `config/fsm.yaml` | 状态超时、重试次数、速度、容差、安全策略和资源清单 |
| `config/robot_poses.yaml` | 左右臂拍照位、放置位等 MoveJ 关节姿态 |
| `launch/competition_system.launch.py` | 总启动文件，组装硬件、算法、FSM 和 Qt |

默认使用完整的 `competition_fsm_node`。旧的 `task_sequence_node.py` 作为兼容保留的单商品流程，不应与完整 Competition FSM 混淆。

## 2. 系统总体架构

系统可分为四层：

```text
Qt Competition Console
        |
        | /competition/task, /competition/start, /pause, /stop ...
        v
competition_fsm_node
        |
        | ROS 命令分发、反馈校验、超时、重试、安全停机
        v
CompetitionFSM
        |
        | 当前状态、下一状态、步骤动作、资源声明
        v
底盘 / 升降机 / RM65 / 相机 / YOLO / Qwen / GraspNet / CuRobo / 夹爪
        |
        +---- Action、Service、Topic 结果和反馈 ----> competition_fsm_node
```

### 2.1 CompetitionFSM：流程决策层

`CompetitionFSM` 是纯 Python 核心，不直接调用 ROS。它维护：

- 当前任务 `task`；
- 当前步骤列表 `steps`；
- 当前索引 `index`；
- 运行状态 `READY/RUNNING/ERROR/SAFE_STOP`；
- 当前商品索引和完成数量；
- 重试次数、对象状态和批次计划；
- 当前步骤开始时间，用于超时判断；
- `ResourceManager` 资源状态。

FSM 的步骤使用 `StateStep` 描述：

```text
name                 状态名，例如 OBJECT_1_YOLO_DETECT
phase                所属阶段，例如 OBJECT_TASK_LOOP
module               FSM / CONTROL / PERCEPTION / PLANNING / DRIVER
action               人类可读动作说明
resources            需要占用的资源
navigation_target    导航点
arrival_frame        期望到达事件，例如 ARRIVED_D
conditional          是否为条件分支
```

状态机不会根据“收到一条消息”自动前进，而是执行如下闭环：

```text
当前 state
  -> competition_fsm_node 分发一次动作
  -> 外部设备或算法执行
  -> 外部节点发布结果/反馈
  -> 节点检查结果是否属于当前 state
  -> 生成 FSM event
  -> CompetitionFSM.advance(event)
  -> 进入下一个 state
```

### 2.2 competition_fsm_node：ROS 适配层

节点负责：

1. 订阅 Qt 任务和控制命令；
2. 创建和调用底盘 Action、升降机命令、机械臂 MoveJ、感知触发和夹爪 Service；
3. 订阅 YOLO、Qwen、GraspNet、CuRobo、关节、升降机、夹爪和底盘反馈；
4. 将异步回调转换为 FSM 事件；
5. 用定时器驱动超时检查和真实状态分发；
6. 发布完整的 `/competition/status` telemetry；
7. 在停止、超时、TF 丢失或驱动错误时执行 SAFE_STOP。

节点使用串行化 FSM 回调和锁，避免 ROS 多线程回调同时修改状态。

## 3. 配置与任务建模

### 3.1 任务输入

Qt 通过 `/competition/task` 发布 JSON，例如：

```json
{
  "box_type": "3号箱子",
  "objects": ["果粒橙", "奥利奥", "加多宝", "薯片"]
}
```

任务由 `CompetitionTask.from_dict()` 解析，并由 `CompetitionConfig.resolve_task()` 转换成：

- 箱体配置 `BoxConfig`；
- 商品配置列表 `ObjectConfig`；
- 选择的步骤位；
- 箱体与商品的执行顺序。

### 3.2 商品配置字段

每个商品条目包含：

| 字段 | 含义 |
|---|---|
| `yolo_label` | YOLO 输出类别，例如 `chengzi`、`kele` |
| `qwen_prompt` | YOLO 失败时发送给 Qwen 的语义提示 |
| `arm` | `LEFT` 或 `RIGHT` |
| `lift_height_mm` | 抓取前升降目标高度 |
| `navigation_point` | 首选货架导航点 |
| `retry_navigation_point` | 识别失败时的备用点，可选 |
| `grasp_angles` | 抓取姿态角度优先级 |

例如：

```text
果粒橙：LEFT，D，50 mm，60/45/30°
奥利奥：LEFT，G，530 mm，60/45/30°
加多宝：RIGHT，E，530 mm，-60/-45/-30°
薯片：LEFT，G，50 mm，60/45/30°
```

因此，程序不需要为每一种商品写一份独立流程；商品差异由配置注入统一的商品步骤模板。

### 3.3 三类高度

`config/fsm.yaml` 中定义商品放置阶段的固定高度：

- 抓取高度：由商品条目给出，常见为 50 mm 或 530 mm；
- 放入箱体高度：300 mm；
- 释放高度：200 mm；
- 商品完成后的安全高度：50 mm。

空箱抓取完成后，1、2 号箱保持抓取时的当前高度，运输到 J 点后降至 150 mm；3、4 号箱抓取后调整至 150 mm。随后执行底盘后退、旋转并导航到 J 点；到达后均保持 150 mm，再执行双夹爪打开和双臂回拍照位。

## 4. 顶层状态机

顶层状态为：

```text
SYSTEM_INIT
  -> INIT_BARRIER
  -> WAIT_FOR_TASK
  -> VALIDATE_TASK
  -> EMPTY_BOX_TASK
  -> OBJECT_TASK_LOOP
  -> LOADED_BOX_TASK
  -> FINISHED
```

异常路径为：

```text
任意关键状态失败
  -> ERROR
  -> SAFE_STOP
```

### 4.1 SYSTEM_INIT

建立 FSM、加载配置、清理上一次任务的计数器、重试表、GraspNet 状态和导航状态。此阶段不执行抓取动作。

### 4.2 INIT_BARRIER

初始化 barrier 要覆盖：

- Navigation；
- 升降机反馈；
- 左右机械臂和关节状态；
- 左右夹爪；
- 左右 RGB-D 相机；
- YOLO、Qwen、GraspNet、CuRobo；
- TF；
- Qt bridge。

只有依赖就绪后，系统才进入等待任务状态。

### 4.3 WAIT_FOR_TASK 与 VALIDATE_TASK

Qt 先发送任务，再通过 `/competition/start` 启动。启动回调会检查：

- 是否已经收到任务；
- 箱型是否存在；
- 商品数量和商品名称是否有效；
- 真实执行时是否同时满足 `execute:=true` 和安全令牌。

校验失败不会发送任何真实运动命令。

## 5. 识别方案：从相机到目标确认

### 5.1 RGB-D 采集

左右腕部相机分别使用自己的命名空间：

```text
/left_camera/left_camera/color/image_raw
/left_camera/left_camera/aligned_depth_to_color/image_raw
/left_camera/left_camera/aligned_depth_to_color/camera_info

/right_camera/right_camera/color/image_raw
/right_camera/right_camera/aligned_depth_to_color/image_raw
/right_camera/right_camera/aligned_depth_to_color/camera_info
```

当前参数为 640×480、15 FPS，开启彩色/深度对齐和同步。FSM 同时记录相机、机械臂和 TF 的对应关系，避免左右相机数据串线。

### 5.2 YOLO 首选检测

商品识别首先通过 YOLO：

- 权重：`best.pt`；
- 当前总 Launch 配置 confidence threshold 为 0.3；
- 最大推理频率 5 FPS；
- 启动 warmup，但不自动开启任务推理；
- FSM 在进入商品识别状态时触发检测；
- 只接受与当前 `ObjectConfig.yolo_label` 匹配的结果。

YOLO 的作用是快速提供类别和图像区域，后续 GraspNet 使用同步 RGB-D 生成三维抓取候选。

### 5.3 Qwen 语义兜底

当 YOLO 在规定时间内没有目标，FSM 不直接失败，而是进入对应的 `QWEN_FALLBACK` 状态：

1. 从商品配置取得 `qwen_prompt`；
2. 通过 `/qwen_vl/prompt` 发布 JSON 请求；
3. 请求中带有 `arm` 和 `keyword`，路由到对应腕部数据；
4. 等待 `/qwen_vl/{arm}/result`；
5. 要求结果属于当前商品和当前状态。

Qwen 当前使用单节点双臂模式：模型只加载一次，但左右相机帧、TCP/TF、投票和结果发布器在内部按臂隔离。`temporal_required_votes=1` 表示当前只要求一次有效时间投票。

### 5.4 识别结果验收

识别成功必须同时满足：

- 回调携带的状态与当前 FSM 状态一致；
- 结果的 arm namespace 与任务配置一致；
- YOLO label 或 Qwen prompt 与当前商品一致；
- 图像和深度时间戳同步，容差 0.25 s；
- 导航结果已经转换为当前点的 `ARRIVED_<marker>` 事件；
- 导航到达/机械臂稳定后等待感知 settle delay，当前为 2 s。

### 5.5 识别失败恢复

恢复顺序由 `retry_order` 定义：

```text
YOLO -> QWEN -> CAMERA_REFRESH
```

若 Qwen 仍然超时，商品有备用导航点时先尝试备用点，例如 D↔E、F↔G、H↔I；连续重试超过上限后进入 `ERROR`。

## 6. 抓取候选与姿态选择

### 6.1 GraspNet 触发

商品或箱体识别完成后，FSM 调用：

```text
/{arm}/grasp/trigger
```

GraspNet 节点接收对应相机的 RGB-D、任务目标和角度参数，输出：

- 抓取候选列表；
- 目标位姿；
- 接近方向；
- 候选评分；
- `grasp valid` 状态；
- 与当前帧对应的时间信息。

启动参数中使用 `publish_target=true`、`auto_trigger=false`，由 FSM 明确控制每次触发。

### 6.2 角度优先级

商品配置定义每个商品的角度序列，系统按照顺序严格试探：

- 右臂：`-60° -> -45° -> -30°`；
- 左臂：`60° -> 45° -> 30°`。

箱体通常使用单独的箱体角度配置。角度不是装饰性参数，而是抓取候选搜索空间的一部分，用于改变腕部绕目标的观察/接近方向。

### 6.3 候选接受条件

一个候选只有在以下条件全部成立时才可成为 `selected_grasp`：

```text
grasp valid
AND IK PASS
AND collision PASS
AND trajectory SUCCESS
```

其中：

- `grasp valid`：GraspNet 认为候选几何上可用；
- `IK PASS`：目标位姿能转换为机械臂可达关节解；
- `collision PASS`：规划过程未碰撞；
- `trajectory SUCCESS`：CuRobo 成功生成可执行轨迹。

如果所有角度都失败，FSM 进入：

```text
NO_VALID_GRASP -> REPERCEPTION
```

刷新相机并重新感知，而不是直接闭合夹爪。

## 7. CuRobo 轨迹规划

### 7.1 规划前 barrier

CuRobo 规划前要求两个条件同时满足：

```text
TARGET_READY
AND
COLLISION_WORLD_READY
```

`PlanningAdapter.can_plan()` 只在两者都为真时返回 true。这样可以避免目标位姿或碰撞世界尚未更新时提前规划。

### 7.2 规划参数

当前配置为：

| 参数 | 值 | 作用 |
|---|---:|---|
| `max_attempts` | 30 | 规划失败最大尝试次数 |
| `staged_grasp` | true | 预抓取、接近、抓取分段执行 |
| `high_following` | true/由 Launch 覆盖 | 提高轨迹跟随能力 |
| `interpolation_dt` | 0.008 s | 轨迹插值时间步长 |
| `enable_nvblox` | false | 当前流程不接入 NVBlox 动态碰撞世界 |
| `voxel_size` | 0.015 m | NVBlox 配置预留参数 |
| `collision_margin` | 0.02 m | 碰撞安全裕量 |
|

### 7.3 抓取轨迹阶段

商品抓取通常拆成：

```text
照片位
  -> 预抓取位
  -> 慢速接近
  -> 抓取位
  -> 夹爪闭合
  -> 抬升
  -> 运输/放置位
```

机械臂慢速接近速度由 `slow_approach_mps=0.03` 控制。分阶段执行有利于在目标附近降低速度，并把夹爪闭合放在明确的反馈屏障之后。

### 7.4 双臂箱体规划

箱体抓取时，左右两侧分别进行 GraspNet 和 CuRobo 规划。只有左右规划结果都成功，才能通过：

- `EMPTY_BOX_PLAN_BARRIER`；
- `EMPTY_BOX_EXECUTION_BARRIER`；
- `EMPTY_BOX_PREGRASP_BARRIER`；
- `EMPTY_BOX_APPROACH_BARRIER`。

这保证箱体不会出现“一侧先抓、另一侧还没准备好”的不对称动作。

## 8. 空箱抓取与运输流程

`_box_steps()` 生成空箱阶段步骤。完整顺序如下：

1. `EMPTY_BOX_TASK`：开始空箱任务；
2. `EMPTY_BOX_PHOTO_POSE`：左右臂同时进入拍照位；
3. `EMPTY_BOX_NAVIGATE`：导航到箱体配置点 B 或 C；
4. `EMPTY_BOX_ARRIVAL_KEYFRAME`：匹配 `ARRIVED_B/C`；
5. `EMPTY_BOX_LIFT_PICK`：升降到箱体高度；
6. `EMPTY_BOX_GRIPPER_OPEN`：左右夹爪打开并确认；
7. `EMPTY_BOX_PERCEPTION_LEFT/RIGHT`：左右相机识别箱体；
8. `EMPTY_BOX_QWEN_FALLBACK_LEFT/RIGHT`：YOLO 失败时分别 Qwen 兜底；
9. `EMPTY_BOX_GRASPNET_LEFT/RIGHT`：左右生成候选；
10. `EMPTY_BOX_GRASP_SELECTION`：按角度选择候选；
11. `EMPTY_BOX_CUROBO_PLAN_LEFT/RIGHT`：左右规划；
12. `EMPTY_BOX_PLAN_BARRIER`：等待双侧规划结果；
13. `EMPTY_BOX_EXECUTION_BARRIER`：统一放行双臂执行；
14. `EMPTY_BOX_PREGRASP_BARRIER`：同时到预抓取位；
15. `EMPTY_BOX_APPROACH_BARRIER`：同步慢速接近；
16. `EMPTY_BOX_GRASP_POSE_BARRIER`：同时到抓取位；
17. `EMPTY_BOX_CLOSE_BARRIER`：左右夹爪同步闭合；
18. `EMPTY_BOX_HOLD`：夹爪和机械臂保持；
19. `EMPTY_BOX_LIFT_TRANSPORT`：仅 3、4 号箱执行，抓取后调整至 150 mm；1、2 号箱运输到 J 点后再降至 150 mm；
20. `EMPTY_BOX_AGV_RETREAT`：底盘后退 0.50 m；
21. `EMPTY_BOX_AGV_ROTATE`：底盘原地旋转 180°；
22. `EMPTY_BOX_NAVIGATE_J`：导航到箱体放置区 J；
23. `EMPTY_BOX_LIFT_RELEASE`：降到释放高度 50 mm；
24. `EMPTY_BOX_OPEN_BARRIER`：双夹爪同步打开；
25. `EMPTY_BOX_PHOTO_COMPLETE`：左右臂回拍照位；
26. `EMPTY_BOX_COMPLETE`：阶段完成。

后退不是盲目延时，而是由 `/chassis/odom` 闭环判断位移；导航 Action 的成功结果转换为 `ARRIVED_J`，旧导航回调不会推进新状态。

## 9. 商品抓取与放置流程

`_object_steps()` 为每个商品生成统一步骤。单商品流程如下：

1. 载入商品配置；
2. 导航到商品的 D/E/F/G/H/I 点；
3. 匹配 `ARRIVED_<point>`；
4. 机械臂进入升降安全位；
5. 升降到商品抓取高度；
6. 当前机械臂夹爪打开；
7. 机械臂进入拍照位；
8. 确认相机帧就绪；
9. 再次确认导航到达帧；
10. YOLO 检测当前商品；
11. YOLO 无结果时进入 Qwen fallback；
12. GraspNet 生成候选；
13. 按商品角度顺序筛选；
14. 无有效候选时重新感知；
15. CuRobo 规划抓取轨迹；
16. 到达预抓取位；
17. 慢速接近；
18. 闭合夹爪；
19. 读取位置和 holding 反馈确认抓取；
20. 升降到 `min(current + 50, 500)` 的运输高度；
21. 机械臂回安全/拍照位；
22. 导航到放置区 J；
23. 到达 J 后升降到 300 mm；
24. 机械臂进入放置姿态；
25. CuRobo 规划放置轨迹；
26. 将商品放入箱体；
27. 降到 200 mm；
28. 打开夹爪；
29. 机械臂返回拍照位；
30. 降到 50 mm；
31. 标记商品完成。

### 9.1 商品批次优化

当任务选择了 3 个商品且左右臂分布为 2+1 时，FSM 会将第一个商品与后续第一个异臂商品组成批次。批次流程共享一次去 J 的底盘行程，再按左臂优先、右臂随后放置，从而减少底盘往返。

不需要放置的商品步骤会进入 `HOLDING`，保持对应机械臂和夹爪闭合，等待批次放置。

### 9.2 满载箱运输

商品全部完成后进入 `LOADED_BOX_TASK`：

1. 导航到满载箱抓取点 J；
2. 左右臂进入拍照位；
3. 升降到 50 mm；
4. 双夹爪打开；
5. 左右相机分别识别箱体；
6. 左右 GraspNet 和 CuRobo 分别规划；
7. 通过双臂规划、预抓取、接近和闭合 barrier；
8. 读取双夹爪真实 holding 反馈；
9. 升到运输高度 150 mm；
10. 导航到最终点 A；
11. 到达 A 后降到 100 mm；
12. 双臂打开夹爪放置满载箱；
13. 返回拍照位；
14. 进入 `LOADED_BOX_PLACE_COMPLETE` 和 `FINISHED`。

## 10. 升降机控制逻辑

升降机不是简单发送一次高度后立即执行下一步，而是采用命令确认与实际反馈双重检查：

```text
发送 set_lift_height_cmd
  -> 等待 set_lift_height_result
  -> 读取 udp_lift_state 实际高度和错误标志
  -> 实际高度进入 ±5 mm 容差
  -> 生成 ACTION_COMPLETE
```

主要接口：

- `/left/rm_driver/set_lift_height_cmd`；
- `/left/rm_driver/set_lift_height_result`；
- `/left/rm_driver/udp_lift_state`；
- `/left/rm_driver/set_lift_speed_cmd`。

升降机使用绝对高度，不依赖上一步状态猜测当前位置。超时默认 30 s；安全停机时发布速度 0。

### 10.1 升降安全约束

`forbid_lift_with_arm_extended=true`。在商品流程中，机械臂必须先进入 `ARM_TO_LIFT_SAFE`，才允许升降到抓取高度；抓取完成后也先抬升商品，再回运输姿态。

## 11. 底盘导航与运动逻辑

导航通过：

```text
/chassis/move_to_marker
```

使用 `lh_chassis_interfaces/action/MoveToMarker` Action。每个导航步骤包含：

- 目标 marker；
- 距离容差 0.20 m；
- 角度容差 0.35 rad；
- 超时 300 s；
- 期望到达帧 `ARRIVED_<marker>`。

导航成功后，`NavigationAdapter.match_arrival_frame()` 将 Action success 转换为 FSM 事件。FSM 只接受当前请求对应的 marker，延迟到达回调或旧任务回调会被忽略。

### 11.1 底盘与机械臂互斥

`forbid_base_with_arm_extended=true`。底盘导航前，机械臂必须回拍照位或安全位；箱体流程中，只有双臂保持状态稳定后才允许后退、旋转和导航。

### 11.2 箱体后退和旋转

空箱抓取后，底盘：

1. 通过 odom 闭环后退 0.50 m；
2. 原地旋转 180°；
3. 导航到 J。

底盘停止接口为 `/chassis/stop`，SAFE_STOP 时取消当前 Action 并调用 stop。

## 12. 机械臂与夹爪控制

### 12.1 MoveJ 姿态

`config/robot_poses.yaml` 是机械臂固定姿态的唯一来源，包含：

- `left_photo`、`right_photo`：拍照/安全位；
- `left_place`、`right_place`：商品放置位。

机械臂通过：

```text
/{arm}/rm_driver/movej_cmd
/{arm}/rm_driver/movej_result
```

MoveJ 结果为真后，FSM 才进入下一状态；关节错误通过 `joint_states` 和 `udp_joint_error_code` 监测。

### 12.2 夹爪闭合与抓取确认

夹爪命令接口：

```text
/{arm}/omnipicker_gripper/open
/{arm}/omnipicker_gripper/close
```

闭合命令成功不等于抓取成功。FSM 还要求：

- `position_valid=true`；
- 实际位置达到配置容差；
- `is_holding` 或等价 holding 状态成立；
- 驱动状态没有错误。

夹爪位置来自状态寄存器 22。抓取确认失败时状态为 `UNVERIFIED`，不会假定物品已经被夹住。

### 12.3 故障时夹爪策略

安全策略明确要求：

- 停止时保持夹爪；
- 错误时不自动打开夹爪；
- 由人工确认物品状态后再 reset。

原因是：如果物品已经被抓住，错误时自动 open 可能导致掉落；如果未抓住，则也不应在未知姿态下继续动作。

## 13. ROS 2 接口完整说明

### 13.1 Qt 与 FSM

| 方向 | 接口 | 类型 | 用途 |
|---|---|---|---|
| Qt → FSM | `/competition/task` | `std_msgs/msg/String` JSON | 箱型、商品列表、task_id |

| Qt → FSM | `/competition/pause`、`/resume`、`/stop`、`/reset` | Trigger | 流程控制 |

旧接口 `/supermarket_pick/status`、`/supermarket_pick/competition_start`、`/supermarket_pick/cancel` 用于兼容旧脚本。

### 13.2 设备与算法

| 模块 | 主要接口 |
|---|---|
| 底盘导航 | `/chassis/move_to_marker` Action |
| 底盘停止 | `/chassis/stop` Service |

这些字段使 UI 和现场调试人员能够判断系统停在“导航、升降、识别、抓取、规划还是反馈确认”。

## 14. 超时、重试与安全停机

### 14.1 典型超时

来自 `config/fsm.yaml` 的典型超时：

| 阶段 | 默认超时 |
|---|---:|
| 初始化 | 180 s |
| 任务校验 | 5 s |
| 导航 | 300 s |
| 升降 | 30 s |
| MoveJ | 30 s |
| 相机 | 10 s |
| 感知 | 45 s |
| Qwen | 180 s |
| GraspNet | 180 s |
| CuRobo | 180 s |
| 夹爪 | 15 s |
| 抓取确认 | 15 s |

### 14.2 失败恢复

恢复策略按故障类型分层：

1. 识别无结果：YOLO → Qwen；
2. Qwen 失败：刷新相机；
3. 商品识别仍失败：去备用导航点；
4. 抓取候选失败：按角度尝试下一个候选；
5. 规划失败：重新规划，最多 30 次 CuRobo 尝试；
6. 连续导航/任务失败：达到上限后进入 ERROR；
7. 关键硬件反馈丢失：立即 SAFE_STOP。

### 14.3 SAFE_STOP

进入 SAFE_STOP 后执行：

1. 取消导航 Action；
2. 调用 `/chassis/stop` 停止底盘；
3. 升降机速度置零；
4. 对左右机械臂发布 `move_stop_cmd`；
5. 夹爪保持当前状态，不自动打开；
6. 发布错误原因和状态 telemetry；
7. 等待人工检查并调用 reset。

触发条件包括急停、TF 丢失、关节错误、夹爪反馈无效、规划失败、状态超时和驱动故障。

## 16. 关键设计总结

### 16.1 为什么使用 FSM

移动底盘、双臂、升降机、相机和算法都是异步系统。FSM 为每个动作建立明确的开始、等待、成功、失败和超时边界，避免多个回调直接修改任务顺序。

### 16.2 为什么识别采用 YOLO + Qwen

YOLO 适合快速、结构化的类别检测；Qwen 适合在遮挡、类别变化或标签不稳定时做语义兜底。两者被放在 FSM 的条件状态中，而不是让识别节点直接决定抓取。

### 16.3 为什么抓取候选必须经过多重校验

视觉上“看起来能抓”不代表机械臂可达、无碰撞或轨迹可执行。`valid + IK + collision + trajectory` 四项同时成立，才能将候选转成执行动作。

### 16.4 为什么错误时不自动打开夹爪

系统无法在故障时确定物品是否已被夹持。保持夹爪是更保守的状态，避免物品在未知姿态下掉落；后续处理交给人工复位。

### 16.5 一句话概括

`supermarket_pick_sequence` 的本质是一个以 Competition FSM 为核心、以 ROS 2 事件和反馈为连接、以双臂同步与安全互斥为约束的移动抓取任务编排系统。
