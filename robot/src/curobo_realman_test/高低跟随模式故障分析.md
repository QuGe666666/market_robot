# RealMan CANFD 高低跟随模式故障分析

## 1. 文档目的

本文记录 2026-09-04 在超市抓取全流程中出现的 CuRobo 真机执行故障，供后续复现、日志判定和代码维护使用。

故障原始信息：

```text

status=0(IDLE) allowed=[5]; point=99
commanded_motion=0.030217rad
feedback_age=0.003553s
command_period=0.008175s
overruns=0 max_schedule_lag=0.000000s
```

本次启动参数和执行诊断均确认：

```text
curobo_high_following:=false
high_following=false
```

因此，这不是高跟随执行，而是低跟随执行被错误套用了高跟随状态检查。

## 2. 高跟随与低跟随

发送到 `/{arm}/rm_driver/movej_canfd_cmd` 的 `Jointpos.follow` 决定控制模式：

| 配置 | `Jointpos.follow` | 含义 | 状态检查 |
| --- | --- | --- | --- |
| `high_following=true` | `true` | 控制器严格跟随连续透传点，周期必须不超过 10 ms | 开始产生有效运动后必须进入状态 `5` |
| `high_following=false` | `false` | 控制器根据自身速度、加速度追踪透传点，可能丢弃来不及到达的中间点 | 允许状态 `0` 或 `5`，以关节反馈判断是否真实运动 |

RealMan 状态码中：

```text
0 = IDLE，使能但空闲
5 = MOVE_THROUGH_JOINT，角度透传
9 = EMERGENCY_STOP，急停
10 = SLOW_STOP，缓停
11 = PAUSE，暂停
```

状态 `0` 在低跟随模式下不能单独作为拒绝执行的依据。状态 `9` 则是明确的急停状态，必须先按现场安全流程恢复，不能通过忽略状态检查绕过。

## 4. 错误机制

旧判断在经过宽限时间且轨迹产生 0.03 rad 有效运动命令后，无条件要求控制器状态为 `5`：

```python
if require_transparent and should_require_transparent_state(...):
    allowed_statuses = {5}
```

该逻辑只适用于高跟随，却同样作用于 `high_following=false`。因此低跟随状态仍为 `0` 时，软件提前停止轨迹，机械臂还没有获得完成低跟随追踪所需的连续点。

修复后的判断位于：

```text
/home/lh/robot/src/curobo_realman_test/
curobo_realman_test/planner_node.py
```

修复逻辑：

```python
if require_transparent and high_following and should_require_transparent_state(...):
    allowed_statuses = {5}
```

结果：

- 高跟随仍要求状态 `5`，原安全检查没有取消。
- 低跟随允许状态 `0` 或 `5`，不会在第 99 点被误杀。
- 两种模式仍检查反馈新鲜度、关节使能、关节错误、RM 错误、起点偏差、逐点跟随误差和最终到位误差。
- 如果低跟随确实没有运动，后续会以真实关节跟随误差失败，而不是用不适用的状态码失败。

## 5. GraspNet 控制器连接隔离

同一轮日志还显示 GraspNet 在候选姿态生成和可行性筛选阶段，单独连接并断开控制器：

```text
Connected to RealMan controller: 169.254.128.18:8080
Disconnected from RealMan controller
```

随后进入的轨迹执行链路是：

```text
CuRobo 规划器生成关节轨迹
  -> CuRobo 规划器按 8 ms 发布 Jointpos
  -> /{arm}/rm_driver/movej_canfd_cmd
  -> rm_driver 接收轨迹点
  -> rm_driver 通过 RealMan SDK/CANFD 下发到机械臂控制器
```

因此，“CuRobo 执行轨迹”和“rm_driver 执行轨迹”描述的是链路中的不同职责。CuRobo 负责规划、定时发布和反馈监控；`rm_driver` 是 ROS 指令到 RealMan 控制器之间的硬件驱动桥，实际控制器命令必须经过它。

GraspNet 本身不负责执行抓取轨迹。旧实现中它连接控制器，是为了读取当前关节角、TCP 位姿和工具坐标系，并使用当前状态进行候选姿态可行性筛选。GraspNet 完成后断开自己的 SDK 连接，再由 CuRobo 触发上述轨迹执行链路。

这不是本轮 `allowed=[5]` 的直接触发条件，但旧实现会让 GraspNet 和 `rm_driver` 分别持有同一控制器的 SDK 会话，增加后续命令链路不确定性。

ROS/FSM 模式已经改为订阅：

```text
/{arm}/joint_states
/{arm}/rm_driver/udp_arm_position
```

每次抓取请求把不可变的关节和 TCP 位姿快照传给 `grasp.py`，不再建立第二个 RealMan SDK 连接。独立运行 `grasp.py` 时仍保留原来的 SDK 直连方式。

修复生效后的 GraspNet 日志应出现：

```text
Using immutable ROS joint/TCP snapshot; no secondary RealMan SDK connection will be opened.
```

如需专门验证高跟随，可显式使用：

```text
curobo_high_following:=true
```

高跟随验证必须满足：发送周期不超过 10 ms、有效运动后状态进入 `5`、无持续增大的关节跟随误差。不能通过关闭跟随误差保护来掩盖轨迹或通信问题。

## 7. 下次运行的判定标准

正常低跟随运行应满足：

1. `EXEC_DIAG_START` 显示 `high_following=false`。
2. GraspNet 显示使用 ROS 状态快照，不再显示连接和断开 RealMan 控制器。
3. 不再出现 `status=0(IDLE) allowed=[5]`。
4. CSV 中关节反馈随命令变化，`max_error_rad` 不持续增长到保护阈值。
5. 轨迹结束后进入到位判断并返回成功。

如果仍然不动，应优先检查最新 CSV：

- `published=1` 且反馈完全不变：继续查 DDS 到 `rm_driver` 回调以及控制器是否接收 CANFD 指令。
- `command_period_s` 大量超过 0.010 s：查 CPU/GPU 负载和调度超期。
- `feedback_age_s > 0.5`：查 UDP 实时上报和 ROS 反馈链路。
- 状态 `9`：机械臂处于急停，先执行现场安全恢复。
- 关节错误码非 0 或使能标志为 0：先处理驱动和机械臂本体错误。

`RTPS_TRANSPORT_SHM open_and_lock_file failed` 和 `A message was lost` 可能由临时启动多个 `ros2 topic echo` 进程、高频状态话题或 Fast DDS 共享内存端口冲突引起。如果执行诊断中的反馈仍然新鲜且周期正常，它们不能单独解释机械臂不运动。
